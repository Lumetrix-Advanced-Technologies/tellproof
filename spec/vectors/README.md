# Test vectors

The contract every verifier must meet: `internal/pack` (Go, used by `plumbline-verify`), `web/verify/verify.js` (browser), `concierge/verify.py` (Python) and, in Plumbline's own repository, the original reference page's tests. They are published under the Apache License 2.0 so that anyone can check a verifier of their own against them.

- `pass/`: three chained packs for the fictional Kestrel Assist (synthetic telemetry). They must verify, in order.
- `fail/`: one envelope per failure mode. Each fails exactly the checks listed in `manifest.json`.
- `manifest.json`: every case, its previous pack (for the chain check) and the expected result object `{signature, subject_digest, chain, merkle, verified}`.
- `test-jwks.json`, `test-public-key.pem`: the issuer key for these vectors.
- `test-private-key.pem`: **TEST ONLY.** It signs nothing but these vectors. Never use it for a real pack, never load it outside tests.
- `make_vectors.py`: regenerates everything with the same key. Only rerun it when the format changes (for example D-008, the predicateType domain), and commit the new files in the same PR as the format change. Never regenerate to make a failing test pass.
- `extra/` and `extra-manifest.json`: cases beyond the core manifest that every verifier must agree on (a pack with no disclosed trace, a batch-typed envelope, an unknown kid, and packs that must be refused: `expect: "error"`). Generated by `make_extra_vectors.py` from pass vector 1 with the same test key; it reads the existing vectors and never changes them (D-018).
- `keys/` and `key-manifest.json`: key-status cases (D-042). Pass vector 1 checked against fourteen JWKS files: `nbf`/`exp` windows and their boundaries, rotation, revocation, and malformed key sets every verifier must refuse to load (`expect: "jwks_error"`). Generated by `make_key_vectors.py`; no pack is signed or changed.
- `../jcs-vectors.json`: canonical-JSON cases, including the ones Go's `encoding/json` gets wrong.

Run all of it: `make vectors`.

## Writing your own verifier

A reviewer who would rather not run our code can write their own verifier and check it here. The formats:

- **Envelope:** DSSE. The signature is ECDSA P-256 with SHA-256, DER-encoded, over `PAE(payloadType, payload)`; `keyid` is the `kid` of a key in the issuer's JWKS (Plumbline's issuer uses the key's RFC 7638 thumbprint).
- **Payload:** an in-toto Statement v1 in RFC 8785 canonical JSON. The subject digest is the SHA-256 of the canonical predicate. The predicate's schema is `../pack.schema.json`.
- **Chain:** `prev_pack_digest` is `"sha256:"` and the hex SHA-256 of the previous pack's decoded payload bytes (`manifest.json`'s `chain_rule`).
- **Merkle proof** (a disclosed trace): leaf `sha256(0x00 || salt16 || utf8(trace_id))`, node `sha256(0x01 || left || right)`; an odd node at the end of a level is carried up unchanged, and the proof (`{side: "L" | "R", hash}` from leaf to root) has no entry for that level.
- **Keys:** a signature counts only if the key's `nbf ≤ issued_at < exp` (whole seconds, when present) and the key is not in the JWKS's `revoked` list.

A verifier is correct when, for every case:

1. `manifest.json`: verifying `file` (with `prev`, when given, as the previous pack) against `test-jwks.json` gives exactly `expect`: `{signature, subject_digest, chain, merkle, verified}`, where `null` means the check does not apply.
2. `extra-manifest.json`: the same, and a case whose `expect` is `"error"` is refused rather than reported.
3. `key-manifest.json`: verifying `file` against the case's `jwks` gives `expect`, and `"jwks_error"` means the key set itself must be refused.
4. `../jcs-vectors.json`: each `input` canonicalises to exactly `expected`, and every `must_reject` input is refused.

If your verifier disagrees with ours on any case, one of us has a bug. Please report it privately (see `SECURITY.md`). A confirmed case becomes a new vector: vectors are only ever added, never changed.
